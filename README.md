# AI-помощник для подготовки товарных описаний B2B

Локальный прототип на Python для генерации черновиков товарных карточек контрольно-измерительных приборов (КИПиА) для B2B-интернет-магазина. 

Решение ориентировано на предотвращение технических галлюцинаций, прозрачную обработку неполных сведений, программную фиксацию метрологических характеристик и переносимость между облачными и локальными LLM.

---

## 1. Стек технологий

- **Язык:** Python 3.10+ (протестировано на Python 3.13 / 3.11).
- **Менеджер пакетов и проекта:** [`uv`](https://docs.astral.sh/uv/).
- **Интерфейс:** Streamlit.
- **Валидация данных и схемы:** Pydantic v2.
- **Клиенты LLM:**
  - `google-genai` — официальный SDK для Gemini API.
  - `openai` — клиент для OpenAI-совместимых облачных сервисов и локальных серверов (LM Studio, Ollama, vLLM, LocalAI).
- **Тестирование:** `pytest` (с изоляцией и моками сетевых запросов).

## 2. Установка и запуск

### 2.1. Установка менеджера `uv` (если не установлен)
Инструкция по установке доступна на [официальном сайте uv](https://docs.astral.sh/uv/getting-started/installation/). В Windows через PowerShell:
```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

### 2.2. Установка зависимостей проекта
В корневой папке проекта выполните команду:
```powershell
uv sync
```
`uv` автоматически создаст виртуальное окружение `.venv` и установит все необходимые зависимости из `pyproject.toml`.

### 2.3. Настройка конфигурации (`.env`)
Создайте файл `.env` на основе примера `.env.example`:
```powershell
cp .env.example .env
```
Заполните параметры провайдера:

#### Вариант А: Использование Google Gemini
```dotenv
LLM_PROVIDER=gemini
LLM_MODEL=gemini-2.5-flash
LLM_API_KEY=ваш-секретный-ключ-api
LLM_BASE_URL=
LLM_OUTPUT_MODE=json_schema
LLM_TIMEOUT_SECONDS=120
LLM_MAX_RETRIES=2
LLM_FALLBACK_ENABLED=false
```

#### Вариант Б: Использование локального сервера (LM Studio / Ollama)
```dotenv
LLM_PROVIDER=openai_compatible
LLM_MODEL=qwen2.5-7b-instruct
LLM_API_KEY=
LLM_BASE_URL=http://localhost:1234/v1
LLM_OUTPUT_MODE=json_prompt
LLM_TIMEOUT_SECONDS=180
LLM_MAX_RETRIES=2
LLM_FALLBACK_ENABLED=false
```

#### Резервный маршрут (Fallback)
При необходимости включите резервный маршрут:
```dotenv
LLM_FALLBACK_ENABLED=true
LLM_FALLBACK_PROVIDER=openai_compatible
LLM_FALLBACK_MODEL=meta-llama-3.1-8b-instruct
LLM_FALLBACK_API_KEY=
LLM_FALLBACK_BASE_URL=http://localhost:1234/v1
LLM_FALLBACK_OUTPUT_MODE=json_prompt
```

### 2.4. Запуск веб-приложения
```powershell
uv run streamlit run app.py
```
После запуска интерфейс будет доступен в браузере по адресу `http://localhost:8501`.

## 4. Правила валидации и обработка неполных данных

1. **Защита от опечаток и мусорных данных:**
   - Дублирующиеся ключи в JSON отклоняются специальным парсером на базе `object_pairs_hook`.
   - Неизвестные поля верхнего уровня отклоняются.
   - Значения характеристик должны быть строками либо `null`. Числа, массивы и объекты отклоняются с указанием имени конкретного поля.
2. **Минимум для запуска генерации:**
   - Обязательно наличие непустых полей `name` и `manufacturer`.
   - Обязательно наличие хотя бы одной характеристики с известным значением **ИЛИ** непустого исходного описания.
3. **Проверка ожидаемых характеристик категории (`category_profiles.json`):**
   - Пользователь может выбрать категорию оборудования (например, *«Манометры и датчики давления»* или *«Термопреобразователи и датчики температуры»*).
   - Приложение ищет ожидаемые характеристики (с учетом синонимов и алиасов).
   - Если ожидаемая характеристика отсутствует во входе, она автоматически вносится в таблицу со значением **«данных нет»**, а контент-менеджер видит предупреждение.
4. **Подтверждение продолжения:**
   - При наличии предупреждений генерация блокируется до явной установки чекбокса:
     > *«Продолжить с неполными данными. Отсутствующие характеристики будут отмечены как «данных нет».»*
   - Любое изменение входных данных сбрасывает подтверждение и помечает ранее созданную карточку как неактуальную.

## 5. Структура результата и защита от галлюцинаций

Карточка товара состоит из пяти блоков:
- **`seo_title`**: заголовок страницы (до 70 символов включительно).
- **`seo_description`**: технически выверенное описание (строго от 800 до 1200 символов с пробелами).
- **`specs_list`**: список характеристик прибора. **Формируется программно**, а не генерируется моделью, что гарантирует 100% сохранение оригинальных диапазонов, погрешностей и единиц измерений.
- **`search_queries`**: от 3 до 5 релевантных B2B-запросов.
- **`commercial_block`**: краткий текст (1–3 предложения) о целевой аудитории и задачах.

### Приоритет достоверности над объемом
Модели строго запрещено додумывать неподтвержденные параметры (степень защиты, поверку, материалы, цены, гарантию). Если модель не может сформировать карточку без домыслов, она сообщает об этом через поле `insufficient_data_reason`.

## 6. Логика повторов, исправления и Fallback

1. **Повторы сетевых запросов (Retries):**
   - Повторяются только временные сбои (таймауты, сетевые разрывы, ошибки 5xx, rate limits 429) с экспоненциальной задержкой (1с, 2с, 4с...).
   - Ошибки авторизации (401/403) и неверные имена моделей не повторяются.
2. **Корректирующая генерация (Self-Correction):**
   - Если модель нарушила требования по длине описания (меньше 800 или больше 1200 символов), числу запросов или формату JSON, выполняется **ровно одна** повторная корректирующая попытка с указанием конкретных нарушений.
3. **Резервный маршрут (Fallback):**
   - Срабатывает только при исчерпании повторов основного маршрута или провале корректирующей попытки.
   - Не запускается при ошибках авторизации (неверный API-ключ) или некорректной конфигурации.
   - Факт использования fallback и фактическая модель фиксируются в метаданных и интерфейсе.

## 7. Запуск автоматических тестов

Тестовый набор покрывает валидацию, парсинг JSON, обработку профилей категорий, программную сборку `specs_list`, повторные попытки при сбоях и механизм fallback:
```powershell
uv run pytest tests/ -v
```

Все тесты изолированы и используют моки, поэтому запуск не требует реальных API-ключей или сетевого подключения.

## 8. Ограничения MVP и дальнейшие улучшения

- **Проверка фактов в свободном тексте:** Автоматическая сверка каждого утверждения свободного текста с исходными данными пока не реализована — перед публикацией обязательна ручная вычитка контент-менеджером.
- **Противоречия в данных:** Неявные противоречия между текстом паспорта и таблицей характеристик в MVP могут остаться незамеченными моделью.
- **Поддержка PDF:** Распознавание сканов и PDF-паспортов вынесено за рамки MVP.
